## What the numbers say

**KV cache (CPU rows).** At 1,024 prompt tokens, decoding with the cache takes 56 ms per token and recomputing everything takes 2,084 ms: **~37x**. At 16 tokens the gap nearly disappears, because each step is dominated by reading every weight once, not by the prefix. Without a cache, total work grows with the square of the sequence; with it, each new token costs one position.

**Decode is bandwidth-bound; prefill is compute-bound.** Decode tokens/s barely moves with prompt length. Prefill runs 10–60x faster per token because one weight read serves many tokens.

**From 20 to 66 tok/s on the GPU: the wins, in the order they were found.**

| step | decode tok/s (16-token prompt) | what changed |
|---|---:|---|
| PyTorch ops on MPS, bf16 weights | ~20 | baseline |
| hand-written Metal kernels (matvec, RMSNorm, RoPE, attention, SwiGLU) | ~41 | fewer, fused dispatches; matvec at 77–86 GB/s |
| + fused QKV, fused SwiGLU, fused residual | ~37–39 | within noise: dispatch count was not the bottleneck |
| + remove `int(positions[0])` inside every layer | ~68 (profiled) | that line forced the CPU to wait for the GPU 24x per token |
| + embedding lookup on the GPU instead of CPU-then-copy | **~66** end to end (77 in a pure GPU loop) | the copy blocked on all queued GPU work |

The profile before the last two fixes showed CPU issue time (23.1 ms) equal to wall time (23.2 ms): the GPU was idle, waiting for Python. After them the CPU issues a token's work in 1.6 ms and the GPU runs it in ~13 ms: **GPU-bound, at 60–65% of the bandwidth ceiling**. The same fixes lifted the plain PyTorch backend from ~20 to ~43 tok/s.

**Lesson worth remembering:** the biggest speedups came from removing hidden GPU→CPU synchronizations, not from kernel cleverness. Anything that reads a GPU value on the CPU (`int()`, `.item()`, `.cpu()`, a CPU→GPU copy of freshly computed data) serializes the two processors.

**What remains.** The output head alone reads 272 MB per token (3.1 ms at 86 GB/s). Beyond that, the remaining gap to the ceiling is kernel efficiency (matvec reaches 77–86 of ~100 GB/s) and the per-token readback of the sampled id, which a real serving loop also pays. Weight quantization (Weeks 11–12) attacks the byte count itself.

## Week 10: the native bridge and a hand-written GEMM

**Native Objective-C++ runtime** (`src/native/metal_runtime.mm`, built by `scripts/build_native.sh`, called through `ctypes`). It owns its own `MTLDevice`, command queue and pipeline, compiles the same `matvec.metal` source at runtime, and keeps weights in shared (unified-memory) buffers. Encoding 50 dispatches into one command buffer and waiting once: 896x896 matvec in 19 us (vs 25 us through PyTorch's per-call dispatch), 4864x896 at 88 GB/s, the 151,936-row output head at 79 GB/s. A CPU write through a Python view of a shared buffer is visible to the GPU with no copy.

**Tiled GEMM for prefill** (`src/kernels/gemm.metal`): 16x16 threadgroup-memory tiles, each weight reused 16x. Correct to 1e-6, but 0.29 TFLOP/s against ~1.2 TFLOP/s for PyTorch's MPS GEMM, which uses the GPU's matrix units (`simdgroup_matrix`) and larger register tiles. The backend therefore keeps PyTorch's GEMM for prefill and uses custom kernels for decode, where they win. Closing the gap would mean `simdgroup_matrix` 8x8 tiles and double-buffered loads.

No Xcode is installed, so Instruments / `xctrace` GPU traces are unavailable here; profiling used wall-clock vs CPU-issue timing and `cProfile` (section above), which was enough to find both sync bottlenecks.
