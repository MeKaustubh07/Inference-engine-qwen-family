# Week 8 benchmark: KV cache and backends

Generated by `scripts/bench.py`. Each backend runs in its own process.

### What the numbers say

- **The KV cache matters more as context grows.** At 16 prompt tokens the cache barely helps (70.9 vs 93.5 ms per token on CPU): recomputing 16 tokens is cheap next to reading 2 GB of weights. At 1,024 tokens, recomputing costs 1,862 ms per token against 63 ms with the cache, **~30x**. Without a cache, total work grows with the square of the sequence length; with it, each new token costs one position.
- **Decode is bandwidth-bound; prefill is compute-bound.** Decode speed barely moves with prompt length because each step is dominated by reading every weight once. Prefill processes many tokens per weight read, so its tokens/s is 10–50x higher than decode's.
- **The GPU reaches only ~20% of its bandwidth ceiling (~20 of ~101 tok/s).** Per token, the model launches hundreds of small GPU operations from Python and converts activations between fp32 and bf16 around every matrix multiply. That overhead, not weight reads, dominates. This is the target for the hand-written Metal kernels in Weeks 9–10.
- **CPU fp32 needs twice the bytes.** fp32 weights are 1.98 GB, so its ceiling is ~51 tok/s. Resident memory: 2.6 GB for CPU fp32, 445 MB for MPS bf16 (weights live in unified memory on the GPU side).
- Caveat: TTFT for the CPU 1,024-token cached run (2.3 s) is higher than the uncached one (1.3 s), although both run the same prefill math. Treat single-run CPU TTFT as noisy; thermal state and scheduling on a fanless laptop move it by this much.
