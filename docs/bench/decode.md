## Reading the numbers

**KV cache (CPU rows).** At 1,024 prompt tokens: 53 ms per token with the cache, 1,512 ms without, **~28x**. At 16 tokens the gap shrinks to ~2x because each step is dominated by reading every weight once, not by the prefix. Without a cache, total work grows with the square of the sequence; with it, each new token costs one position.

**The bandwidth ceiling is the floor on decode time, not a description of where time went.** Every decode step must read all resident weights once, so ~100 GB/s ÷ weight bytes caps tokens/s. The backends reach 33–72% of that cap. What fills the rest differs: fixed per-step overhead (hundreds of dispatches, per-token readback of the sampled id) and, at long context, attention over the KV cache (the Metal backend falls from 73 to 49 tok/s between 16 and 1,024 tokens of context). Prefill is compute-bound instead: it reaches 490–1,312 tok/s because one weight read serves many tokens.

**From ~20 to ~73 tok/s on the GPU (16-token prompt), in the order the wins were found:**

| step | decode tok/s | what changed |
|---|---:|---|
| PyTorch ops on MPS, bf16 weights (before sync fixes) | ~20 | baseline |
| hand-written Metal kernels | ~41 | matvec at 77–86 GB/s, fused norm/RoPE/attention |
| + fused QKV, SwiGLU, residual | ~37–39 (noise) | dispatch count was not the bottleneck |
| + stop reading `int(positions[0])` from the GPU in every layer | ~68 (profiled) | removed 24 forced CPU-GPU waits per token |
| + embedding lookup on the GPU (no CPU→GPU copy) | **~73** | removed the last blocking copy |

Before the last two fixes, CPU issue time (23.1 ms) equalled wall time (23.2 ms): the GPU idled waiting for Python. After them the CPU issues a token's work in 1.6 ms and the GPU runs it in ~13 ms. The same fixes lifted plain PyTorch-on-MPS to ~45 tok/s. The biggest speedups came from removing hidden GPU→CPU synchronizations (`int()`, `.item()`, `.cpu()`, a CPU→GPU copy of fresh data), not from kernel cleverness.

**Memory.** `ru_maxrss` only counts CPU pages; the Metal driver's allocation (weights, KV cache, PyTorch's caching allocator) is reported separately (~2 GiB, of which ~1 GB is bf16 weights and the rest cached allocator blocks). Figures are MiB.

## Week 10: the native bridge and a hand-written GEMM

**Native Objective-C++ runtime** (`src/native/metal_runtime.mm`, built by `scripts/build_native.sh`, called through `ctypes`): its own `MTLDevice`, command queue and pipeline; compiles the same `matvec.metal` at runtime; weights in shared unified-memory buffers. Encoding 50 dispatches into one command buffer: 896x896 matvec in 19 us (vs 25 us via PyTorch's per-call dispatch), 4864x896 at 88 GB/s, the 151,936-row output head at 79 GB/s. A CPU write through a Python view of a shared buffer is visible to the GPU with no copy.

**Tiled GEMM for prefill** (`src/kernels/gemm.metal`, 16x16 threadgroup tiles): correct to 1e-6 but 0.29 TFLOP/s vs ~1.2 TFLOP/s for PyTorch's MPS GEMM, which uses the GPU's matrix units (`simdgroup_matrix`). Prefill therefore keeps PyTorch's GEMM; decode uses the custom kernels, where they win.

No Xcode is installed, so Instruments / `xctrace` GPU traces are unavailable; profiling used CPU-issue vs wall timing plus `cProfile`, which found both sync bottlenecks.
